Rewrite of a batch-manufacturing platform

With agentsGxPSWPLC2026

The platform pharmaceutical plants use to write, approve and run batch recipes, rebuilt from the ground up in .NET 10. It covers recipe authoring and execution, the PLC bridge and the audit trail.

Who owns this
Owner
Trac d.o.o. owns the product and the code. It is not public.
Data
Test system only, no customer data
My role
Top contributor, working on the recipe engine, the chart control, the PLC test rig, the robot's migration and the validation documents

The starting point

The original platform has grown since 2020 and runs at hundreds of installations with thousands of users. I had worked on it for years, mostly on its recipe editor. In 2026 the team rebuilt it from scratch on .NET 10. The recipe editor, the engine that runs batches, the bridge to the PLCs and the lab robot's orchestrator are now separate services around one API.

What I built

  • The recipe engine. I rebuilt it on the team's earlier state-machine design. Every kind of recipe step has its own state machine, so Hold, Stop and Abort behave the same on every step. Live values reach the operator stations over SignalR, and the clients reconnect on their own.
  • Crash recovery. The engine writes its run state to a temporary file and then renames it, so after a restart it can rebuild every running batch from that file and the live PLC.
  • Outages. Failed API calls wait in a queue and are replayed in order, so a short outage never loses a report or an audit row.
  • The recipe-chart control came over from my old editor, and I extended it with sub-recipes, conditional branches, loops and IEC 61131-3 transition notation. The editor and the server check recipes against the same rules.
  • Hardware-in-the-loop tests drive a real PLC and check the database, and each one names the requirement and the OQ test it proves.
  • I moved the lab robot's services onto the new platform, so they only talk to the API and never go straight to the database.
  • Validation documents. I wrote the URS, FS, SDS, HDS and user manual for the engine, plus the OQ protocols, and they're all approved.

How I worked

  • About 40 services are injected through interfaces. I wrote small fakes for the PLC and the API, so the engine runs in unit tests without either.
  • The tests also use real hardware, not only fakes.
  • I write the specification and the plan, coding agents write the code, and I review every change before it goes in.

A lab sample-preparation robot

By handSWPLCGxP2023 to 2026

A modular robot that prepares pharmaceutical samples for analysis. I wrote most of its module software, nearly all of its PLC code, and the camera service that finds the sample tubes.

Who owns this
Owner
Trac d.o.o. It is not public.
Status
In development, not released yet
My role
Module software, PLC code, the camera, deployment and logging

The robot

A gantry arm moves sample tubes between the dosing, weighing, homogenizing and extraction modules. Each module is its own small machine, with a Raspberry Pi that runs both its PLC program and its software, and a touchscreen for the operator. A host orchestrator runs the batch across all of them.

The software in the modules

  • All six services share one core, so a fix to the PLC link or the audit trail reaches all of them at once. Each module plugs its own operations into the core.
  • Every operator command is an object that checks the mode, the machine's state and the user's rights before anything is written to the PLC, and every write goes to the audit trail.
  • Screens recover by themselves. Every open screen shares one OPC UA subscription per tag. Requests made during an outage wait, and everything subscribes again after a reconnect.
  • Each module describes itself in one file that lists its operations, recipe parameters, alarms and OPC UA addresses, so the host configures it without code changes.
  • Each Pi reports its health to the PLC by writing its temperature, memory, disk and network figures to tags, and the module lights follow the batch state.

Driving the arm

  • A game controller drives the arm. Node can't read gamepads, so my first version ran a headless browser to read the controller and wrote jog, speed, gripper and mode commands to the PLC over OPC UA every 20 ms. Later I built it into the arm's touch screen, where it sends only what changed and stops every axis if the controller disconnects or the page closes. by hand, 2025
  • Service screens. Every axis and the rotary gripper have a press-and-hold jog that stops on release, lost focus or a hidden tab. There's also a go-to-position panel and a four-step calibration wizard, whose new offsets reach the PLC only after an electronic signature, with each change logged in the audit trail. jog by hand 2025, calibration with agents 2026
  • Operators can set the pickup moves, up to eight retract, rotate and wait steps per module slot. I built this through every layer, from the PLC data types and arm logic to the transfer between controllers, the module service and the settings screen. with agents, 2026
  • From a recipe to arm moves. In the orchestrator I wrote the step that adds the arm transfers between modules and the measurements a later step depends on. At the end it sends each tube to disposal or back to its rack. by hand, 2024 to 2026

The PLC code in the controllers

  • The code runs on seven controllers with four shared libraries. The ISA-88 phase library is the company's, and the module programs on top of it are mine.
  • All 35 operations extend one abstract base. Its final method turns the host's batch commands into Run, Hold, Stop and Abort, so every operation answers the host the same way.
  • My own serial library. It's a generic, object-oriented library for our machines, where each device, like a balance or a chiller, brings its own command set and response parser. The RS-485 master polls them in turn, retries, and skips any device that stops answering.
  • Safety and alarms. The interlocks live with the arm itself. There's also an alarm engine with acknowledgement and a ring buffer, and a simulation controller for testing sequences without hardware.
  • Motion fixes on the real machine. On the servos I fixed the missing enable-operation bit, the positioning-alarm reset and a setpoint bit left set after a halt. On the step motors I fixed a start that could fire before the new move data arrived, and the rotary gripper got a watchdog for a trigger left set. by hand, 2024 to 2025
  • Status lights you can read across the lab. The PLC sets an output, a small service on the Pi forwards it over serial, and an ESP32 draws a colour and motion for each of 15 batch states. by hand, 2025

The camera

  • I trained and compared YOLO models across iterations, keeping every run with its settings and scores, then wrapped the best one in a long-running service the orchestrator drives over stdin and stdout.
  • The camera checks itself and reopens when it fails or goes stale. Blurry or badly lit photos are retaken before detection, and detections are mapped onto the rack's real geometry.

Testing without a machine

  • Two Raspberry Pi soft-PLCs act as a simulated plant. They run 18 simulated operations that batch recipes can start and simulate the plant utilities too, so the batch engine can be tested end to end without the robot. with agents, 2026
  • Screens without a machine. Every touch screen has a mock mode, and a Playwright tool walks all six through every screen state for a screenshot gallery. with agents, 2026
  • PLC code reviewed like any other code. A parser turns CODESYS exports into plain Structured Text, so every PLC change shows up as a git diff. A second tool builds the specification's event list from the module files and the PLC source. with agents, 2026

Keeping the fleet running

  • My deploy tool builds, copies and restarts every Pi over SSH, and checks that each service really came back. Logs from every module and every PLC go to one place (Loki and Grafana).
  • When the Pis kept dropping their PROFINET link, I traced it to timing and moved them to a real-time Linux kernel. Worst-case latency fell from 301 µs to 94 µs.

The bartender demo, Christmas 2022

For the company Christmas party, the robot's batch engine poured drinks. Guests picked juice or one of three brandies on a touch screen and set how much they wanted, up to 50 ml. The kiosk started the batch recipe over SignalR and locked the screen until the drink was ready. I wrote the kiosk in Blazor WebAssembly, and opened the batch engine to the browser with its own port and CORS policy. by hand, 2022

What it does

How it fits together

What I built

  • Walls between customers. Tests fail the build when a new table or endpoint isn't covered.
  • Security. Webhooks connect only to an address that has already been checked, which closes a known trick for reaching internal servers. Print links are signed and short-lived, and sign-in tokens rotate with reuse detection.

  • Shipping. Every push builds a Docker image, and the server pulls it automatically.

The connection to QuickBooks and Xero for accounting sync is in place, and sending invoices to them comes next.
